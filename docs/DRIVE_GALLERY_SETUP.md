To refresh sooner, open **GitHub → website → Actions → Build and deploy website → Run workflow → main**. Ordinary CMS saves also trigger a refresh. No additional Porkbun or DNS change is needed for the gallery.

## How to name uploads

Use **firstname_lastname_target.jpg**. The first two underscore-separated parts identify the photographer. Every remaining part belongs to the target name. `astro_target` is a placeholder for the target, not a required literal prefix.

| Drive filename | Website target/title | Credit |
|---|---|---|
| `jane_doe_andromeda_galaxy.jpg` | Andromeda Galaxy | Image by Jane Doe |
| `alex_smith_M31.webp` | M31 | Image by Alex Smith |
| `anna-marie_McDonald_NGC_7000.png` | NGC 7000 | Image by Anna-Marie McDonald |
| `jane_doe_orion_nebula_widefield.jpg` | Orion Nebula Widefield | Image by Jane Doe |

Lowercase words become title case. Catalog identifiers such as M31, NGC and IC are capitalized. Existing mixed case or uppercase is preserved, so use `McDonald` when that is the intended spelling. Use a hyphen within a multipart given/surname, such as `anna-marie_de-la-cruz_M31.jpg`, because underscores separate the fields. For two photographs of the same target, add a useful distinguishing phrase to the target or use separate filenames; duplicate Drive names produce separate pages, but a CMS correction by filename applies to both.

Use processed, still **JPEG, PNG, TIFF (.tif/.tiff) or WebP**, up to **200 MiB** and **120 megapixels** per original. Full pixel dimensions are preserved; responsive previews are generated automatically. Manual CMS uploads use the same image limits, although the editor/provider may impose a lower upload limit. RAW, FITS, HEIC, animated images, multipage TIFF, videos, folders and shortcuts are not imported. See [gallery image quality](GALLERY_IMAGES.md) for full-size zoom, color-depth and hosting limits. Only direct children of the selected folder are read; subfolders are not searched. Incorrectly named images are skipped with an explanation in the Actions log. A corrupt, oversized or undownloadable correctly named photo stops the deployment so the previous website stays live.

This folder is a publishing destination. Tell contributors that uploading there means the photo and the name in its filename will appear publicly on the club website, with their permission. Give upload access to intended contributors. The folder itself can remain restricted; website visitors receive optimized website copies and do not need Drive access.

## One-time administrator setup

First upload the updated website source to GitHub and complete the main [launch guide](LAUNCH_GUIDE.md), including Pages and CMS. Then:

The credential needed here is a **service-account JSON key**, created under **IAM & Admin → Service Accounts**. A standard **API key**, created under **APIs & Services → Credentials → API key**, does not authorize access to a restricted Drive folder. Do not paste either credential into chat or repository files. If an unused website API key has already been shared, delete it from **APIs & Services → Credentials**; if it is used elsewhere, rotate it and update those applications. [Google's authentication explanation](https://docs.cloud.google.com/docs/authentication/api-keys#standard-api-keys), [key handling guidance](https://docs.cloud.google.com/docs/authentication/api-keys-best-practices).

The folder's **Shared with me** location is supported. You do not need to move it into My Drive. The folder owner or someone allowed to manage its sharing must share **Member_Photos** directly with the service-account email as Viewer; access granted to your personal Google login does not automatically extend to that account.

1. Open [Google Cloud Console](https://console.cloud.google.com/) under the account that will administer this club integration. Select/create a club project, for example **PAC Website Gallery**. In **APIs & Services → Library**, find **Google Drive API** and choose **Enable**. Enable the IAM API if the console asks while creating the account. [Google's API setup instructions](https://developers.google.com/workspace/guides/enable-apis).
2. Open **IAM & Admin → Service Accounts → Create service account**. Name it **pac-gallery-reader**. Skip the optional project-role and user-access grants; it does not need Project Editor/Owner or domain-wide delegation. Create the account and copy its email address, which ends in `iam.gserviceaccount.com`. This is a dedicated automated reader. [Google's service-account instructions](https://docs.cloud.google.com/iam/docs/service-accounts-create).
3. In Drive, open the [selected folder](https://drive.google.com/drive/folders/1ovIgPYF6oufpNY4W8Q5RCMW9IeUFvaXR), choose **Share**, add that service-account email, and grant **Viewer** access. Ensure viewers may download the photos. Separately grant upload access to the intended club contributors. The reader does not need permission to edit or delete files. If a Purdue-managed account blocks sharing with this address, ask its administrator to permit that specific sharing arrangement or use an approved club-controlled folder; domain-wide access is unnecessary.
4. Back in Google Cloud, select the service account → **Keys → Add key → Create new key → JSON**. Download the key. Keep it private, outside the website folder. If organizational policy blocks keys, a maintainer can configure Workload Identity Federation instead; do not weaken an organization policy just for this setup. [Google's key instructions](https://docs.cloud.google.com/iam/docs/keys-create-delete).
5. Open the repository's **Settings → Secrets and variables → Actions → Secrets → New repository secret**. Name it exactly **`DRIVE_GALLERY_CREDENTIALS_JSON`**. Paste the **entire JSON file contents** as its value, then save. Use a secret, not a variable or repository file. For the current repository, the settings page is [Actions secrets](https://github.com/purdue-astronomy-club/website/settings/secrets/actions). Use the actual owner if you transfer the repo. [GitHub's secret instructions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
6. Open [Pages CMS](https://app.pagescms.org/), select **website → main → Drive Gallery Settings**. The folder ID is already **`1ovIgPYF6oufpNY4W8Q5RCMW9IeUFvaXR`**. Turn **Import photos automatically** on and Save. This starts the build. A successful live import replaces the included initial photos using the same page addresses, without creating duplicates. Every published gallery image also joins the homepage carousel automatically.
7. Upload one approved photo using the naming convention. Run **Build and deploy website** manually, then check [the gallery](https://purdueastro.club/gallery/) after the deployment succeeds. Verify the target title, photographer credit, larger photo view, and phone layout. Rename the same Drive file, refresh again, and verify the caption/credit updates while its page address stays stable. Move that test photo out of the folder and refresh to verify withdrawal.

The unattended GitHub build uses the Google service account and the read-only Drive scope. The Drive connection used in this chat is separate; signing into Drive here does not give GitHub ongoing access. The key is read from the build environment, never written into the site, source ZIP, or photo cache. Never paste it into chat or upload it to the repository. Rotate/revoke the key in Google Cloud when administrators change and replace the GitHub secret with the new key.

## Where to edit afterward

**Photos:** upload, rename, replace or remove the file in [Google Drive](https://drive.google.com/drive/folders/1ovIgPYF6oufpNY4W8Q5RCMW9IeUFvaXR).

**Corrections and settings:** open [Pages CMS](https://app.pagescms.org/) → **website → main → Drive Gallery Settings → Optional photo corrections**. Add the exact Drive filename, including extension. You can supply a better target title, photographer credit, image description, caption, or hide the photo. Blank text fields fall back to the filename. Add a descriptive image description when possible; automatic alt text can only identify the target and photographer. If you rename the file, update its correction's filename too. All published photos join the homepage carousel, which can be hidden as a whole in Homepage Settings.

**Manually written showcases:** use **Astrophotography Showcase** in CMS for images with a longer story or equipment details. Those remain independent of Drive. Avoid publishing the same photo through both methods unless you want two entries.

Generated Drive entries are rebuilt automatically and do not appear as individual editable records under **Astrophotography Showcase**. Their corrections live in **Drive Gallery Settings**, including a spelling correction for Markarian’s Chain. Corrections work for both the included initial photos and live imports. **Show the initial imported photos when live sync is off** controls the included launch copies. To withdraw all Drive photos, turn both that switch and **Import photos automatically** off, then Save. Manually entered photography remains independent.

## Updates, removals and recovery

- The importer copies files to the website and produces responsive WebP sizes plus a full-resolution lossless viewing copy. Original filenames, Drive file links/IDs and the private folder's contents are not embedded in public photo pages. Page addresses use stable hashed references. The folder ID is in the public source settings; it is not a credential or a substitute for Drive permissions.
- Downloaded originals are held in memory only. Imported website copies are oriented at full pixel dimensions, stripped of embedded EXIF and comments, and encoded losslessly before being cached or written to the site. ICC color profiles are retained. Full-size PNG is used when an image exceeds WebP’s dimension limit. Credits remain visible on the site. Drive originals are unchanged. The cache contains only sanitized images and import metadata, never the Google key or token.
- Renaming/replacing an existing Drive file updates its metadata/image on the next successful sync without changing its page address. Deleting and uploading a new file creates a new address, because Google assigns it a different file ID.
- Removing, trashing or moving a photo out of the folder withdraws it after a successful full listing, build and deployment. Hiding an exact filename in CMS also withdraws it. Existing browser/search caches may retain previously public copies.
- A Drive outage, incomplete folder listing or failed download stops the deployment, preserving the existing live site. Check **Actions** for the error, correct access/file format, and rerun. To publish other changes during an extended outage, disable live importing in CMS. Keep the initial-photo switch on to show the ten launch photos, or turn it off too to withdraw Drive photography until re-enabled. This does not delete the Drive originals.
- Initial web copies are stored under `assets/drive-gallery-snapshot`, including a manifest of approved titles/credits. They are build inputs rather than directly served files. Live mode uses only the current Drive listing, so removing a photo from Drive does not make its old initial copy reappear on the website. Previously published copies can still exist in repository history or external caches.
- Scheduled runs in public repositories may be disabled by GitHub after 60 days without repository activity. An owner should check/re-enable the workflow after breaks and run it manually. See the [administrator handoff](ADMIN_HANDOFF.md).

## Maintainer notes

`scripts/sync_drive_gallery.py` runs before calendar/image generation in `scripts/build.py`. It lists only the configured folder using paginated Drive API v3 calls, supports shared-drive folders, requests `capabilities.canDownload`, and downloads image blobs with `files.get?alt=media`. It rejects incomplete/repeated pagination before applying removals. Photo IDs are hashed for stable page references; sanitized cached images are reused when content metadata is unchanged. API failures are reported without token or key contents.

`data/drive_gallery.yml` is editable through `.pages.yml`. Generated content is mounted from `.generated/content/drive-gallery` into Hugo's existing astrophotography section. Images go through the same responsive pipeline and existing accessible gallery/detail/lightbox templates. The ignored `.generated/drive-gallery` cache is restored by production Actions; it is not needed for correctness and can be deleted to force downloads. `PAC_OFFLINE=1` skips Drive entirely and uses the included initial photos when `use_snapshot` is on, including CMS corrections; otherwise it omits Drive entries from that preview. It never contacts the live folder or changes the deployed site. Pull-request checks receive no Drive credentials.

Local configured builds require `DRIVE_GALLERY_CREDENTIALS_JSON` in the process environment. Do not place a key in a shell command, shared terminal history, tracked file, or printed log. Use the GitHub secret for routine production builds.

Official API references: [folder queries and file downloads](https://developers.google.com/workspace/drive/api/guides/search-files), [complete/paginated listings](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list), [service-account credentials](https://google-auth.readthedocs.io/en/latest/reference/google.oauth2.service_account.html).
